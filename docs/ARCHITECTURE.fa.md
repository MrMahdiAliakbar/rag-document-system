<a id="architecture-fa-overview"></a>
## 📌 معرفی پروژه

RAG Document System یک سامانه پرسش و پاسخ مبتنی بر اسناد است که با استفاده از معماری Retrieval-Augmented Generation یا به اختصار RAG پیاده‌سازی شده است.

این سامانه به کاربران اجازه می‌دهد اسناد DOCX را بارگذاری کنند. سپس متن اسناد استخراج شده، به بخش‌های کوچک‌تر تقسیم می‌شود، برای هر بخش بردارهای Embedding تولید می‌شود و اطلاعات به همراه بردارها در پایگاه داده PostgreSQL با استفاده از افزونه pgvector ذخیره می‌شوند.

پس از آن، کاربران می‌توانند درباره اسناد بارگذاری‌شده سؤال بپرسند. سیستم محتوای مرتبط را بازیابی می‌کند و با استفاده از یک مدل زبانی بزرگ (LLM)، پاسخی بر اساس اطلاعات بازیابی‌شده تولید می‌کند.

هدف اصلی سیستم این است که پاسخ‌ها بر پایه محتوای اسناد بارگذاری‌شده باشند، نه صرفاً دانش عمومی مدل زبانی.

<a id="architecture-fa-high-level"></a>
## 🧩 معماری کلی سیستم

برنامه از چند لایه اصلی تشکیل شده است که برای پردازش اسناد و پاسخ‌گویی به پرسش‌ها با یکدیگر همکاری می‌کنند.

### ۳.۱ لایه API

Django REST Framework درخواست‌های HTTP ورودی را مدیریت می‌کند و امکانات برنامه را در قالب API در اختیار کاربران قرار می‌دهد.

این لایه امکانات زیر را فراهم می‌کند:

- بارگذاری، مشاهده فهرست، دریافت جزئیات، ویرایش و حذف اسناد.
- ارسال پرسش درباره اسناد بارگذاری‌شده.
- مشاهده تاریخچه پرسش‌ها.

### ۳.۲ لایه پردازش اسناد

این لایه وظیفه تبدیل فایل‌های DOCX بارگذاری‌شده به محتوای قابل جست‌وجو را بر عهده دارد.

وظایف آن شامل موارد زیر است:

- خواندن فایل‌های DOCX.
- استخراج محتوای پاراگراف‌ها و جدول‌ها.
- تقسیم متن استخراج‌شده به بخش‌های کوچک‌تر.
- تولید Embedding برای هر بخش.
- ذخیره محتوای اسناد و بردارهای Embedding در پایگاه داده.

### ۳.۳ لایه جست‌وجوی برداری

این لایه پرسش کاربر را به یک بردار Embedding تبدیل می‌کند و با استفاده از معیار فاصله کسینوسی، مرتبط‌ترین بخش‌های اسناد را جست‌وجو می‌کند.

فقط بخش‌هایی که دارای Embedding معتبر هستند و به اسناد با وضعیت `completed` تعلق دارند، وارد فرایند بازیابی می‌شوند.

### ۳.۴ لایه RAG

لایه RAG فرایند پرسش و پاسخ را هماهنگ می‌کند.

این لایه بخش‌های مرتبط را بازیابی می‌کند، آستانه فاصله تعیین‌شده را اعمال می‌کند، متن زمینه را می‌سازد و پرسش و محتوای بازیابی‌شده را برای مدل زبانی ارسال می‌کند.

### ۳.۵ لایه LLM

این لایه با استفاده از LangChain و OpenRouter با مدل زبانی تنظیم‌شده ارتباط برقرار می‌کند.

مدل، پرسش کاربر و متن بازیابی‌شده از اسناد را دریافت می‌کند و بر اساس اطلاعات ارائه‌شده پاسخ تولید می‌کند.

<a id="architecture-fa-document-processing"></a>
## 📄 فرایند پردازش اسناد

هنگامی که یک سند بارگذاری می‌شود، مراحل زیر انجام می‌شوند:

۱. API فایل بارگذاری‌شده را اعتبارسنجی می‌کند.

۲. یک رکورد برای سند در پایگاه داده ایجاد می‌شود.

۳. وضعیت سند به `processing` تغییر می‌کند.

۴. فایل DOCX باز می‌شود.

۵. محتوای پاراگراف‌ها و جدول‌ها استخراج می‌شود.

۶. متن استخراج‌شده با استفاده از روش تقسیم‌بندی مبتنی بر توکن به بخش‌های کوچک‌تر تقسیم می‌شود.

۷. برای بخش‌های تولیدشده، Embedding محاسبه می‌شود.

۸. سیستم بررسی می‌کند که تعداد بردارهای تولیدشده با تعداد بخش‌های متن برابر باشد.

۹. بخش‌های قبلی سند در یک تراکنش پایگاه داده با بخش‌های جدید جایگزین می‌شوند.

۱۰. متن کامل استخراج‌شده در فیلد مربوط به سند ذخیره می‌شود.

۱۱. وضعیت سند به `completed` تغییر می‌کند.

اگر پردازش یک سند تازه بارگذاری‌شده با شکست مواجه شود، وضعیت آن به `failed` تغییر می‌کند و پیام خطا ذخیره می‌شود.

اگر هنگام ویرایش یک سند، پردازش فایل جایگزین با شکست مواجه شود، اطلاعات و فایل قبلی سند بازیابی می‌شوند.

<a id="architecture-fa-chunking"></a>
## ✂️ روش تقسیم متن به بخش‌ها

سیستم از روش تقسیم‌بندی مبتنی بر تعداد توکن استفاده می‌کند.

برای توکن‌سازی متن، Tokenizer مربوط به مدل `intfloat/multilingual-e5-small` بارگذاری می‌شود.

| تنظیم | مقدار |
|---|---|
| اندازه هر بخش | ۴۵۰ توکن |
| هم‌پوشانی بخش‌ها | ۶۰ توکن |
| گام حرکت | ۳۹۰ توکن |

گام حرکت از فرمول زیر به دست می‌آید:

`Chunk Step = Chunk Size - Chunk Overlap`

وجود هم‌پوشانی باعث می‌شود بخشی از اطلاعات و ارتباط معنایی میان بخش‌های مجاور حفظ شود و احتمال از دست رفتن مفهوم در مرز میان دو بخش کاهش پیدا کند.

<a id="architecture-fa-embedding"></a>
## 🧠 روش تولید Embedding

سیستم برای تبدیل متن به بردارهای عددی از مدل `intfloat/multilingual-e5-small` و کتابخانه FastEmbed استفاده می‌کند.

| تنظیم | مقدار |
|---|---|
| مدل | intfloat/multilingual-e5-small |
| تعداد ابعاد بردار | ۳۸۴ |
| پیشوند متن سند | `passage:` |
| پیشوند پرسش | `query:` |
| اندازه هر Batch | ۱۶ |

هر بخش از سند به یک بردار ۳۸۴ بعدی تبدیل می‌شود و با استفاده از pgvector در PostgreSQL ذخیره می‌شود.

پرسش‌های کاربران نیز با همان مدل به بردار تبدیل می‌شوند.

این مدل برای متن اسناد و پرسش‌های جست‌وجو از پیشوندهای متفاوت استفاده می‌کند تا با روش مورد انتظار آن برای بازیابی اطلاعات هماهنگ باشد.

<a id="architecture-fa-vector-search"></a>
## 🔎 جست‌وجوی برداری

در فرایند جست‌وجوی برداری، پرسش کاربر به یک Embedding تبدیل شده و با بردارهای ذخیره‌شده برای بخش‌های اسناد مقایسه می‌شود.

سیستم از معیار Cosine Distance برای اندازه‌گیری فاصله میان بردار پرسش و بردار هر بخش سند استفاده می‌کند.

مراحل جست‌وجو به این صورت است:

۱. برای پرسش کاربر یک Embedding تولید می‌شود.

۲. بخش‌هایی انتخاب می‌شوند که Embedding آن‌ها خالی نباشد.

۳. فقط بخش‌های متعلق به اسناد با وضعیت `completed` در جست‌وجو قرار می‌گیرند.

۴. در صورت ارسال `document_id`، جست‌وجو به همان سند محدود می‌شود.

۵. فاصله کسینوسی میان بردار پرسش و بردارهای ذخیره‌شده محاسبه می‌شود.

۶. نتایج بر اساس فاصله کسینوسی به ترتیب صعودی مرتب می‌شوند.

۷. حداکثر تعداد بخش‌های تعیین‌شده توسط Top-K بازگردانده می‌شوند.

هرچه مقدار Cosine Distance کمتر باشد، میزان شباهت بیشتر است.

<a id="architecture-fa-question-answering"></a>
## 💬 فرایند پرسش و پاسخ

هنگامی که کاربر پرسشی ارسال می‌کند، مراحل زیر انجام می‌شوند:

۱. API پرسش و شناسه اختیاری سند را اعتبارسنجی می‌کند.

۲. پرسش به یک بردار Embedding تبدیل می‌شود.

۳. سیستم مرتبط‌ترین بخش‌های اسناد را جست‌وجو می‌کند.

۴. نتایج بر اساس فاصله کسینوسی مرتب می‌شوند.

۵. فقط بخش‌هایی نگه داشته می‌شوند که فاصله آن‌ها از حداکثر فاصله کسینوسی تعیین‌شده بیشتر نباشد.

۶. اگر هیچ بخش مرتبطی پیدا نشود، سیستم بدون فراخوانی LLM یک پاسخ از پیش تعریف‌شده مبنی بر نبود اطلاعات مرتبط برمی‌گرداند.

۷. در غیر این صورت، بخش‌های بازیابی‌شده به‌صورت منابع مشخص آماده می‌شوند و متن زمینه ساخته می‌شود.

۸. پرسش و متن زمینه از طریق OpenRouter برای مدل زبانی ارسال می‌شوند.

۹. پاسخ تولیدشده از نظر وجود نشانگر مخصوص ناکافی بودن اطلاعات بررسی می‌شود.

۱۰. اگر این نشانگر وجود داشته باشد، پاسخ تولیدشده با پیام از پیش تعریف‌شده نبود اطلاعات جایگزین می‌شود.

۱۱. پرسش، پاسخ و اطلاعات منابع در پایگاه داده ذخیره می‌شوند.

۱۲. API پاسخ نهایی، منابع و وضعیت استفاده از LLM را برمی‌گرداند.

بنابراین سیستم دو حالت برای نداشتن پاسخ معتبر دارد:

- **هیچ بخش مرتبطی پیدا نشود:** مدل زبانی فراخوانی نمی‌شود و مقدار `used_llm` برابر `false` است.
- **مدل زبانی ناکافی بودن اطلاعات را تشخیص دهد:** مدل فراخوانی می‌شود، اما پاسخ نهایی با پیام از پیش تعریف‌شده جایگزین می‌شود. در این حالت مقدار `used_llm` برابر `true` است.

<a id="architecture-fa-database"></a>
## 🗄️ طراحی پایگاه داده

سیستم از سه مدل اصلی برای ذخیره اطلاعات استفاده می‌کند.

### ۱۰.۱ مدل Document

اطلاعات مربوط به اسناد بارگذاری‌شده را ذخیره می‌کند.

فیلدهای مهم:

- `title`: عنوان سند.
- `file`: فایل DOCX بارگذاری‌شده.
- `full_text`: متن استخراج‌شده از سند.
- `status`: وضعیت پردازش سند.
- `error_message`: جزئیات خطای پردازش.
- `created_at`: زمان ایجاد رکورد.
- `updated_at`: زمان آخرین به‌روزرسانی.

مقادیر وضعیت سند:

| وضعیت | توضیحات |
|---|---|
| `pending` | سند ایجاد شده اما هنوز پردازش نشده است |
| `processing` | پردازش سند در حال انجام است |
| `completed` | پردازش سند با موفقیت پایان یافته است |
| `failed` | پردازش سند با شکست مواجه شده است |

### ۱۰.۲ مدل DocumentChunk

محتوای استخراج‌شده و تقسیم‌شده اسناد را ذخیره می‌کند.

فیلدهای مهم:

- `document`: ارتباط با سند اصلی.
- `content`: متن بخش.
- `chunk_index`: موقعیت بخش در سند.
- `embedding`: بردار عددی ۳۸۴ بعدی.
- `metadata`: اطلاعات تکمیلی بخش.
- `created_at`: زمان ایجاد رکورد.

هر بخش به یک سند تعلق دارد. با حذف سند، بخش‌های مرتبط با آن نیز حذف می‌شوند.

### ۱۰.۳ مدل QuestionAnswer

تاریخچه پرسش‌ها و پاسخ‌ها را ذخیره می‌کند.

فیلدهای مهم:

- `question`: پرسش ارسال‌شده.
- `answer`: پاسخ تولیدشده یا پیام از پیش تعریف‌شده.
- `sources`: اطلاعات منابع بازیابی‌شده که در قالب JSON ذخیره می‌شوند.
- `created_at`: زمان ایجاد رکورد.

وضعیت‌های `answered` و `no_answer` که در پاسخ API نمایش داده می‌شوند، از محتوای پاسخ محاسبه می‌شوند و به‌عنوان یک فیلد مستقل در مدل پایگاه داده ذخیره نشده‌اند.

<a id="architecture-fa-error-handling"></a>
## 🛡️ مدیریت خطا و پایداری

سیستم سناریوهای مختلف خطا را مدیریت می‌کند:

- فایل‌های نامعتبر در مرحله اعتبارسنجی رد می‌شوند.
- اسنادی که متن قابل‌خواندن ندارند، با موفقیت پردازش نمی‌شوند.
- در صورت شکست پردازش یک سند تازه بارگذاری‌شده، وضعیت آن به `failed` تغییر می‌کند و پیام خطا ذخیره می‌شود.
- اگر پردازش فایل جایگزین هنگام ویرایش سند شکست بخورد، اطلاعات و فایل قبلی بازیابی می‌شوند و API پاسخ HTTP `422` برمی‌گرداند.
- پرسش‌های نامعتبر توسط API رد می‌شوند.
- خطاهای مربوط به تنظیمات یا تولید پاسخ توسط LLM با HTTP `503` برگردانده می‌شوند.
- در صورت نبود محتوای مرتبط، سیستم پیام از پیش تعریف‌شده نبود پاسخ را برمی‌گرداند.
- عملیات پایگاه داده برای جایگزینی بخش‌های یک سند در قالب تراکنش انجام می‌شوند تا سازگاری داده‌ها حفظ شود.

## 🔌 معماری API

API در سه بخش اصلی سازمان‌دهی شده است.

| نقطه پایانی | توضیحات |
|---|---|
| `/api/documents/` | مشاهده فهرست و بارگذاری اسناد |
| `/api/documents/{id}/` | دریافت، ویرایش و حذف سند |
| `/api/qa/ask/` | پرسش و پاسخ |
| `/api/qa/history/` | تاریخچه پرسش‌ها |
| `/api/qa/history/{id}/` | جزئیات یک رکورد تاریخچه |
| `/api/docs/` | Swagger UI |
| `/api/redoc/` | ReDoc |
| `/api/schema/` | مشخصات OpenAPI |

نقاط پایانی اسناد برای مدیریت فایل‌ها استفاده می‌شوند و نقاط پایانی پرسش و پاسخ، قابلیت‌های RAG و دسترسی به تعاملات قبلی را فراهم می‌کنند.

## 🐳 معماری استقرار

پروژه برای اجرای سرویس‌های خود از Docker Compose استفاده می‌کند.

پیکربندی فعلی شامل دو سرویس اصلی است:

### سرویس PostgreSQL

- از تصویر Docker با نام `pgvector/pgvector` استفاده می‌کند.
- ذخیره‌سازی اطلاعات و قابلیت جست‌وجوی برداری را فراهم می‌کند.
- اطلاعات پایگاه داده را در یک Docker Volume دائمی ذخیره می‌کند.
- پورت پایگاه داده را روی `127.0.0.1:5432` در دسترس قرار می‌دهد.

### سرویس Django Web

- برنامه را با استفاده از Dockerfile پروژه می‌سازد.
- سرور توسعه Django را اجرا می‌کند.
- برنامه را روی پورت `8000` در دسترس قرار می‌دهد.
- به سرویس PostgreSQL متصل می‌شود.
- برای تنظیمات برنامه از متغیرهای محیطی استفاده می‌کند.
- داده‌های Cache مدل‌های Embedding را در یک Docker Volume نگهداری می‌کند.

پیکربندی فعلی Docker برای توسعه و آزمایش در نظر گرفته شده است و یک پیکربندی آماده برای محیط عملیاتی (Production) محسوب نمی‌شود.
